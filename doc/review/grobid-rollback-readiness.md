# GROBID rollback readiness — measured

**Дата проверки:** 2026-09-28
**Срез:** M513-r7dg4z / S01 / T03
**Метод:** `.docker/verify_rollback_readiness.sh` — запуск откатного релиза, не чтение записи о нём

## Зачем это отдельная запись

`.docker/grobid-release.override.yml` сам предупреждает: локально закэшированный
образ **не является долговечной гарантией** — он может исчезнуть при
`docker image prune`, и тогда документированная команда отката падает с
`No such image`. Это уже случалось однажды и осталось незамеченным, потому что
никто не проверял. Откатная цель, которую никто не поднимал, — это допущение,
а не готовность.

## Идентичность релизов

| Роль | Тег | Дайджест |
|---|---|---|
| production | `grobid/grobid:0.9.1-crf` | `sha256:223957791ac2bbe48609dcc58a689b16b60baeae13a8734ef440ae6bfb38f4cd` |
| rollback | `grobid/grobid:0.9.0-crf` | `sha256:24ba90eb1c959f65d812bcdb2cf79c677fa5fd7b95235de616b8bc9fa1317849` |

Суффикс `crf` — вариант моделей (CRF), не версия. 0.9.1 — новейший релиз GROBID
(опубликован 2026-08-04), новее не существует. Локальный vendor-источник
(`/root/vendor-source/grobid`) — тоже 0.9.1, тег `0.9.1`.

## Результат прогона

```
STEP 1 rollback image present locally
STEP 2 rollback container started on 127.0.0.1:8071
STEP 3 rollback service answered version=0.9.0
STEP 4 rollback drill container removed
STEP 5 live production service reports version=0.9.1 (declared release intact)
ROLLBACK-READY rollback=0.9.0-crf observed=0.9.0
```

Что это доказывает:

1. Образ отката **присутствует** (иначе шаг 1 сообщил бы о получении по дайджесту,
   а при недоступности — отказал бы).
2. Образ отката **поднимается и отвечает**: живой сервис из
   `sha256:24ba90eb1c95…` вернул `version=0.9.0` через `/api/version`. Это не
   запись в файле, а прочитанная версия работающего процесса.
3. Откат **не задевает продуктивную работу**: живой контейнер
   `daily-archive-grobid` не останавливался и не пересоздавался, он продолжает
   сообщать `0.9.1`; на момент проверки — uptime 6 дней, healthy.
4. Обе версии **различимы по факту**: продакшен отвечает 0.9.1, откат — 0.9.0,
   поэтому проверка не может пройти на неверном образе.

## Чего эта запись не доказывает

- **Процедуру переключения.** Дрель поднимает откатный релиз на отдельном порту
  (8071) как одноразовый контейнер и удаляет его; она намеренно не выполняет
  замену продуктивного контейнера, чтобы проверка готовности не могла стать
  простоем. Сама команда замены остаётся документированной в
  `.docker/grobid-release.override.yml`.
- **Пригодность откатного релиза для текущих данных.** Проверено, что он
  запускается и сообщает версию; не проверялось, что он даёт те же результаты
  разбора на текущем корпусе. Для отката это отдельный вопрос.
- **Устойчивость образа во времени.** Локальное присутствие не вечно; скрипт
  восстанавливает образ по дайджесту, и именно это делает проверку
  повторяемой, но само наличие образа нужно подтверждать при каждой проверке.

## Как повторить

```bash
bash .docker/verify_rollback_readiness.sh
```

Выход 0 — откат готов; выход 1 — с указанием шага, на котором проверка упала.
Порт дрели переопределяется `GROBID_ROLLBACK_DRILL_PORT`, таймаут старта —
`GROBID_ROLLBACK_DRILL_TIMEOUT`.
