Abstract
Retrieval-augmented generation (RAG) agents are increasingly deployed to answer
questions over local knowledge bases that cannot be centralized due to knowledgesovereignty constraints. This results in two recurring failures in production: users
do not know which agent to consult, and complex questions require evidence
distributed across multiple agents. To overcome these challenges, we propose
RIRS, a training-free orchestration framework to enable a multi-agent system
for question answering. In detail, RIRS summarizes each agent’s local corpus
in an embedding space, enabling a user-facing server to route queries only to
the most relevant agents, reducing latency and avoiding noisy "broadcast-to-all"
contexts. For complicated questions, the server can iteratively aggregate responses
to derive intermediate results and refine the question to bridge the gap toward a
comprehensive answer. Extensive experiments demonstrate the effectiveness of
RIRS, including its ability to precisely select agents and provide accurate responses
to single-hop queries, and its use of an iterative strategy to achieve accurate, multistep resolutions for complex queries.

Introduction

Retrieval-augmented generation (RAG) improves the reliability of large language model (LLM)
applications by grounding model outputs in retrieved external evidence (Wu et al., 2024c; Asai
et al., 2023a; Lewis et al., 2020; Jiang et al., 2023; Izacard & Grave, 2020; Mallen et al., 2022;
Kasai et al., 2024; Xiong et al., 2024; Weng, 2023; Roucher, 2024; Joshi et al., 2024). In practice,
this capability is often deployed as a RAG agent backed by a private corpus. However, enterprise
knowledge is rarely centralized: different business units, products, or teams often maintain separate
RAG agents over disjoint corpora, such as internal documentation, contracts, incident reports, or
partner data (Addison et al., 2024; Wu et al., 2024a;b). Centralizing these corpora into a single
repository (Figure 1a) is typically infeasible due to governance constraints, access controls, and
confidentiality requirements. Moreover, as we show in Section 3.2, centralization is not only desirable
due to knowledge sovereignty constraints, but also hurts retrieval quality and downstream reasoning.
This setting raises a fundamental systems question: how can a user-facing server answer questions
when the relevant evidence is distributed across multiple specialized RAG agents and cannot be
pooled into a single repository?
A natural orchestration strategy is broadcast-to-all: as illustrated in Figure 1b, a user-facing server
forwards each query to every RAG agent, aggregates their responses, and repeats this process until
a final answer is produced. In this system, each agent retains its local, domain-specific knowledge
base, ensuring that its knowledge sovereignty is well protected and that its data are not merged into a
centralized repository. However, broadcast-to-all is inefficient in practice: (i) it wastes computation
and communication because many agents are irrelevant to a given query, (ii) it increases end-to-end
latency by waiting for slow agents and processing long concatenated responses, and (iii) it can
degrade answer quality because excessively long and noisy context makes it easy for the model to

Existing routing methods generally fall into two categories: description-based and learning-based.
Description-based methods rely on manually written descriptions of agent capabilities, allowing an
LLM to select the most suitable agent for a given query based on these descriptions (Patil et al.,
2024; Lu et al., 2024a;b; Yuan et al., 2025; Wu et al., 2025; Zheng et al., 2026). In contrast, learningbased methods train a router on task-specific data to direct each user query to the most appropriate
agent (Lu et al., 2023; Chen et al., 2024a; Ong et al., 2024; Yue et al., 2025; Mei et al., 2025; Wei
et al., 2025; Wang et al., 2026). However, both strategies are difficult to apply in multi-RAG-agent
settings. A textual description may not accurately capture the knowledge boundary of an agent
whose corpus covers multiple subtopics. Learning-based methods are also problematic because the
effective capability of a RAG agent is determined by its non-parametric local corpus, not only by
parametric knowledge, and it is difficult to construct an effective dataset that fully covers that corpus.
Therefore, a routing mechanism in a multi-RAG-agent system should accurately characterize an
agent’s knowledge capabilities without requiring raw data sharing or expensive training.
In this work, we introduce RIRS, a practical orchestration framework that turns a collection of RAG
agents into a single, coordinated problem-solving pipeline via Routing and Iterative Refining-Solving.
Specifically, this framework consists of two modules, namely, knowledge summarization and query
solving. In the knowledge summarization stage, each agent encodes its local corpus, partitions
the resulting embeddings into coherent clusters, and uploads only cluster centroids to the server.
These centroids provide a compact embedding-space summary of the agent’s knowledge capabilities,
while keeping raw knowledge local. In the query-solving stage, the server routes each query to the
most relevant agents by matching the query embedding to the uploaded centroids. For complex
queries, the server then iteratively evaluates partial responses, refines the unresolved question, and
continues querying only the agents needed for the remaining subproblem. In this way, RIRS avoids
broadcast-to-all, preserves knowledge sovereignty, and supports evidence composition across agents
and across rounds.
Contributions.

We summarize the contributions of this paper as follows:

• We study question answering in multi-RAG-agent systems where relevant evidence is distributed
across specialized agents and cannot be centralized because of knowledge-sovereignty constraints.
This setting exposes a key practical challenge: users do not know which agent to query, while
complex questions often require evidence composition across agents.
• We propose RIRS, a training-free framework built on two components: knowledge summarization,
which represents each agent’s local corpus through cluster-level embedding summaries, and query
solving, which selectively routes queries, aggregates partial progress, and refines unresolved
questions across rounds. We also provide a theoretical analysis showing that the routing error of
the centroid-based summary is bounded under a cluster-coherence condition.
• We show that RIRS improves both routing quality and question answering performance. In
particular, it enables more precise agent selection for single-hop queries and more accurate multistep resolution for complex queries, outperforming representative baselines in both effectiveness
and efficiency.

Retrieval Augmented Generation (RAG). RAG has gained substantial interest in academic
research as a robust framework that integrates external knowledge sources into large language models

Shi et al., 2023; Yan et al., 2024; Li et al., 2023b; Press et al., 2022; Chan et al., 2024; Su et al.,

Singh et al., 2025; Li et al., 2025). These advances improve a single RAG pipeline, typically over a
centralized knowledge source. In contrast, our work studies a distributed setting in which knowledge
is partitioned across multiple RAG agents, so the main challenge is not only iterative reasoning, but
also routing the query to the right agents and composing evidence across agents and rounds.
Multi-agent Systems. Multi-agent systems leverage multiple specialized LLM-based agents to
collaboratively solve complex tasks, and have attracted growing attention in recent years (Hong et al.,
2023; Li et al., 2023a; Wu et al., 2023; Chen et al., 2023a;b; Zhao et al., 2023; Guo et al., 2024; Chen
et al., 2024b; Li et al., 2024; Ye et al., 2025; Liu et al., 2026). In question answering, a growing
number of studies improve answer quality through multi-agent collaboration, such as debate- or
discussion-based frameworks in which multiple agents reason over a shared or common knowledge
source to refine candidate answers (Zhang et al., 2025b; Iannelli et al., 2024; Du et al., 2024; Zhang
et al., 2025a). These methods primarily emphasize better coordination and reasoning among agents
once the knowledge source becomes accessible. Different from these works, our focus is not on
having multiple agents reason over the same repository, but on identifying the most relevant agents
when knowledge is inherently distributed across agents.

3

Preliminary and Motivations

This section first reviews the pipelines of a RAG agent and a multi-RAG-agent system (Section 3.1).
We then motivate multi-agent design by showing that multi-RAG-agent systems can consistently outperform single-agent baselines (Section 3.2), and by highlighting why an effective routing mechanism
is crucial (Section 3.3).
3.1

Preliminary

RAG Agent. An RAG agent is an advanced application that integrates retrieval mechanisms with
LLMs to deliver accurate and contextually rich responses. Specifically, an RAG agent processes an
input query through three steps: (i) Knowledge Retrieval: It extracts relevant knowledge pieces using
both sparse and dense retrievers from external sources (Robertson et al., 2004; Izacard et al., 2021;
Xu et al., 2023); (ii) Reranking: It ranks those retrieved pieces with a pretrained regression model to
identify the likelihood of a knowledge piece helpful to the input query, thereby filtering out unhelpful
or misleading information and allowing the generation model to focus on the most pertinent content;
(iii) Response Generation: It combines the question and the pertinent external knowledge to produce
an informed response with its backbone LLM. This process is also known as RankRAG (Yu et al.,
2024). For multi-hop questions, it can adopt EfficientRAG (Zhuang et al., 2024) to iteratively refine
the query and repeat retrieval and generation until the question is resolved.
Multi-RAG-Agent System. A multi-RAG-agent system consists of numerous RAG agents orchestrated under a central entity (i.e., server). When a user query comes, the system should repeatedly
follow these three steps until the query is resolved: (i) the server selects a group of agents and
forwards the query to them; (ii) the chosen RAG agent should give a response to the best of its
local knowledge; (iii) the server aggregates the responses from the selected agents and simplifies
the queries. While answering a given query, an RAG agent is supposed not to expose local raw
knowledge, thereby preserving agent privacy and knowledge sovereignty. Such a system is also
known as the federated RAG system in some recent works (Addison et al., 2024; Shi et al., 2025;
Jung et al., 2025; Zhao, 2024).

RIRS

RIRS is designed for a practical multi-agent QA setting in which knowledge is distributed across
specialized RAG agents, but users still expect a single accurate answer. In this setting, the main
challenge is not only to find relevant agents, but also to combine their partial evidence into a coherent
solution. A useful system therefore needs to do two things well: limit participation to agents that are
likely to help, and continue reasoning when the answer must be assembled across multiple steps.
To make this possible, RIRS decomposes the system into offline and online stages, as illustrated in
Figure 2. At the offline stage (Figure 2a), each agent periodically summarizes the structure of its local
knowledge in the embedding space and shares only a few lightweight representations with the server.
At the online stage (Figure 2b), the server uses these summaries to route the query, judge the quality
of returned responses, and iterate when necessary. In this way, routing and iterative refining-solving

4.1

Offline Agent-Side Preparation: Knowledge Summarization

As shown in Figure 2a, each agent periodically summarizes its local knowledge base into a small
set of centroids for routing. Concretely, an agent splits its local corpus into m chunks and encodes
each chunk into an embedding vector e1 , . . . , em using a shared embedding model, where these
embeddings are cached for later retrieval process. The agent then partitions these embeddings into n
clusters and uploads only the resulting cluster centroids (along with an agent identifier) to the server.
This design preserves knowledge sovereignty by keeping raw knowledge pieces local, while still
allowing the server to estimate which RAG agents are relevant to a query in the embedding space.
To make centroids reliable routing signals, clusters must be internally coherent. If a cluster mixes
semantically unrelated pieces, its centroid degenerates into an "average topic" and becomes a weak
relevance signal. We therefore formulate clustering as a max-min objective that encourages every
cluster to be tight. Let {c1 , . . . , cn } be a partition of {e1 , . . . , em } into n non-empty clusters, and let
sim(·, ·) denote cosine similarity. We maximize the worst-case within-cluster similarity:

4.2

Online Query Solving via Routing and Iterative Refining-Solving

As shown in Figure 2b, the uploaded centroids provide the server with an embedding-space approximation of each agent’s knowledge capability: each centroid represents a coherent region where the
agent is likely to contain supporting evidence. Given a query, the server embeds it and compares the
query embedding with the uploaded centroids to identify the most appropriate agents. After receiving
responses from the selected agents, the server evaluates whether those responses adequately address
the query. If the query is not fully resolved, the server rewrites it to focus on the remaining unresolved
aspects and then repeats the routing and response-evaluation process until a final answer is produced
or no further progress can be made.
Single-round query solving (RTA NS). Given a query q, the server embeds it as x = ϕ(q) using
the same embedding model ϕ(·) used by agents. Let C be the set of all centroids from all RAG
agents, and let f (c̄) map a centroid c̄ to its source agent. The server selects the TopK centroids by
similarity and routes the query to the corresponding agents:

Each selected RAG agent answers the query using its local knowledge and returns an evidence-backed
response. The server then applies Response Evaluator to label each response as addressed vs. not
addressed and curates the round output (e.g., selecting or combining addressed responses). We
denote this single-round procedure as RTA NS (q), which includes: (i) TopK centroid-based agent
selection, (ii) agent response generation with local evidence, (iii) server-side response evaluation, and
(iv) response curation. For single-hop queries, a single RTA NS call is typically sufficient.
Iterative refining-solving for multi-hop queries. For multi-hop queries, the required evidence may
be distributed across agents and across reasoning steps, so a single RTA NS (q) call can be insufficient.
RIRS repeats RTA NS in an iterative loop. At iteration t, the server calls RTA NS (qt ) and uses the
Response Evaluator to label responses as fully addressed, partially addressed, or not addressed. If any
response is fully addressed, the Response Summarizer consolidates the evidence-backed responses
into the final answer and terminates. If only partially addressed responses exist, the server aggregates
partial progress, invokes the Question Simplifier to produce a refined query qt+1 targeting unresolved
aspects, and then proceeds to the next iteration. If all responses are not addressed, the server stops
and reports that the query is unanswerable within the system scope. Full step-by-step procedures and
server-module prompts are provided in Appendix A.
Practical properties. RIRS has three practical advantages. First, centroid-based routing activates
only a small set of relevant agents for each query, reducing fan-out, token usage, and interference
from irrelevant responses. Second, for complex questions, the iterative refining-solving loop turns
partial progress into targeted follow-up queries, enabling evidence composition across agents and
across rounds. Third, RIRS cleanly separates offline knowledge summarization from online query
solving: agents can update local knowledge, refresh their centroids, and synchronize them with the
server, while the server maintains only a lightweight routing index. This separation simplifies new
agent onboarding, supports continuous knowledge updates, and avoids centralizing raw corpora or
retraining a router.

Due to space limits, this section summarizes the experimental setup needed to interpret our quantitative
results. Full implementation details and baseline specifications are provided in Appendix B.
Datasets. Our experiments cover both single-hop and multi-hop open-ended QA tasks within a
unified evaluation framework. We employ the Natural Questions (NQ) dataset (Kwiatkowski et al.,
2019) for single-hop QA to emphasize the effectiveness of the routing mechanism. For evaluating
the performance on answering complex questions, we assess performance on four multi-hop QA
benchmarks: HotpotQA (Yang et al., 2018), 2WikiMultiQA (Ho et al., 2020), MusiQue (Trivedi
et al., 2022b), and Multi-Hop RAG (MHR) Benchmark (Tang & Yang, 2024). Except for MHR, all
questions in these datasets are answerable using knowledge from Wikipedia.
Models. We use text-embedding-v2 (Zhang et al., 2024) to compute dense representations
for retrieval. Agents are powered by two LLM backends: llama-3.1-8b-instruct (Touvron
et al., 2023a;b; Dubey et al., 2024) and qwen-plus-2024-12-20 (Yang et al., 2024a). All
methods are evaluated in an off-the-shelf setting without fine-tuning.
Multi-RAG-Agent Systems. Throughout the experiments, we construct two multi-RAG-agent
systems tailored to different datasets.
• WikiAgents for NQ, HotpotQA, 2WikiMultiQA and MusiQue: WikiAgents group is built upon
a corpus of over 121K Wikipedia pages, dumped as of November 1, 2023, and made publicly
available via the HuggingFace dataset. The system comprises exactly 64 RAG agents. This specific
number is derived from the inherent limitation of the ORES legacy service, which can only classify
a Wikipedia page into 64 predefined categories (Johnson et al., 2021). Consequently, each RAG
agent is designated to handle one of these 64 categories, ensuring that the categorization of pages is
consistent and aligned with the predefined taxonomy established by the ORES service. However,
these agents cannot cover all required documents, and once the question cannot be answered, a
knowledgeable agent will be called to answer the question because the existing LLMs have been
pretrained with the Wikipedia corpus.
• NewsAgents for MHR: NewsAgents group is constructed on a corpus of 609 news articles from
49 distinct news media and spanning six domains (Tang & Yang, 2024). To analyze the effects
of source and domain characteristics, we further split NewsAgent into two variants: NewsAgentSource and NewsAgent-Domain, corresponding to partitions based on news media and domain
categories, respectively. Each agent uses LLaMAIndex to split news articles into 256-token chunks,
with 20 overlapping tokens between consecutive chunks.
Baselines. We compare RIRS with two representative multi-agent routing baselines. Chameleon
(Lu et al., 2024a) is a description-based router that maintains a textual description for each agent and
prompts an LLM to select the most relevant agents for a given query. RouterDC (Chen et al., 2024a)
is a learning-based router that constructs agent representations from single-hop answerable questions
and routes by embedding similarity while keeping the embedding model fixed. Both methods operate
in the same multi-RAG-agent setting as RIRS and serve as alternative routing strategies. Further
implementation details are provided in Appendix B.3.
Evaluation Metrics. We report three metrics. Lexical Match (LM) measures the percentage of
questions whose ground-truth answer string appears in the generated response. GPT Evaluation
(Acc.) uses gpt-4o-2024-08-06 (Achiam et al., 2023) to judge correctness by comparing model
outputs against ground-truth answers while allowing paraphrases. Time measures wall-clock latency
from receiving the question to producing a seemingly valid response; this metric can be noisy due to
network/API variance and runtime contention.

5.2

Ablation Studies

Choice of TopK. Table 3 shows that selecting more clusters increases both agent-level and
document-level answerable rates, which generally improves end-to-end LM/Acc. at the cost of
invoking more agents and viewing more documents. A key observation is that increasing TopK
from 1 to 5 yields a substantial gain, while further increasing it from 5 to 10 brings only marginal
improvement, suggesting diminishing returns beyond moderate agent coverage. Notably, the final
accuracy can exceed the answerable rate because the system falls back to a CoT-only response when
the selected agents are judged unable to answer; in such cases, the LLM may still answer correctly
using parametric knowledge. Finally, document-level answerable rates are consistently lower than
agent-level rates, indicating that even when the right agent is selected, retrieval within its local index
may still miss the most relevant evidence.
5.3 Analysis with Wikipedia-related QA
Table 4 compares the proposed RIRS with representative multi-agent routing baselines on four
Wikipedia-based QA benchmarks under the WikiAgents corpus. We summarize the most salient
findings below.
Comparison with GoldRouter. As an error-free routing mechanism, GoldRouter serves as the
upper bound in a multi-agent system, achieving the highest scores in LM, F1, and Accuracy, as well as
the lowest values in rounds and response time. In contrast, all other methods (Chameleon, RouterDC,
and RIRS) experience varying degrees of performance degradation. i.e., more query rounds but with
lower accuracy. The degradation is owed to routing errors, highlighting the importance of designing
an effective routing mechanism and underscoring the inherent challenge of dynamically estimating
each agent’s expertise on-the-fly.
Comparison with other routing methods. From Table 4, the accuracy ranking among the three
routing methods consistently follows: RIRS > Chameleon > RouterDC, under the same dataset
and backbone LLM. The advantage of RIRS is especially clear on harder multi-hop benchmarks
and with the weaker backbone (LLaMA-3.1-8B), where RIRS improves accuracy by up to 8% over
Chameleon and 15% over RouterDC. These results suggest that RIRS more reliably identifies agent
knowledge boundaries. Concretely, RIRS builds cluster-level representations to characterize each
agent’s knowledge capacity, enabling more accurate routing. By contrast, RouterDC approximates
agent expertise via a fixed cache of historically answerable questions, and Chameleon relies on static
textual descriptions; both signals can be incomplete and lead to misrouting. Notably, while RIRS
may use slightly more rounds than Chameleon, it often runs faster overall because it avoids additional
LLM calls during agent selection.
Comparison with various LLMs. Using a stronger backbone (Qwen-Plus) consistently improves
all methods over LLaMA-3.1-8B, as expected. Moreover, the mixed setting, which uses a stronger
server-side controller (Qwen-Plus) with lightweight agent models, recovers much of the performance
of Qwen-Plus while keeping agent-side costs low. Together with the response-evaluator results in
Table 7, this suggests that a strong evaluator/controller is critical for reducing error propagation
when intermediate agent responses are noisy. This design makes RIRS practical for deployment:
Lightweight models can run at the RAG agents, allowing the underlying knowledge bases to remain
local and generating evidence-backed responses even in resource-constrained settings. Meanwhile,
the user-facing server is equipped with a stronger model to ensure the final response is precise.

Discussion of Different Numbers of RAG Agents. From Table 5 and Figure 3, we observe a tradeoff between granularity and routing reliability. Using more agents provides finer-grained coverage
and typically reduces the number of rounds needed to locate relevant evidence. However, a larger
agent pool also increases routing uncertainty and can hurt accuracy. Compared with GoldRouter,
performance degradation is more pronounced under NewsAgent-Source than under NewsAgentDomain. We attribute this gap to suboptimal agent formation in NewsAgent-Source: partitioning by
news outlets yields agents with diverse, weakly structured topic coverage, which makes it harder to
route queries to the right agents. Besides, the much larger number of agents in NewsAgent-Source
further amplifies routing uncertainty.
A closer comparison between the single-RAG-agent system and NewsAgent-Domain reveals the
existence of an optimal number of agents for a given knowledge base. Using too few agents can
lead to overly broad domain coverage, which reintroduces the challenge of retrieving irrelevant
information. In contrast, the domain-based configuration results in more efficient and accurate
resolution of complex, multi-hop questions.

Conclusion

We study how to reliably answer user queries when knowledge is distributed across multiple business
units and cannot be centralized due to privacy, compliance, or ownership constraints. To this end, we
propose RIRS, an iterative routing framework that coordinates multiple RAG agents while preserving
knowledge sovereignty. RIRS decouples offline knowledge summarization from online query solving:
each agent summarizes its local corpus into centroid-based representations in the embedding space
9

Preprint. Under review.

and maintains these summaries independently, while a user-facing server performs iterative refiningsolving and fuses evidence across agents and rounds. Experiments show that RIRS consistently
outperforms strong multi-agent baselines, and its architecture supports practical deployment: agents
can run lightweight models for grounded generation with local corpora, while the server uses a
stronger model to synthesize reliable responses.

Ethics Statement
This work studies a realistic multi-agent question-answering setting in which knowledge is distributed
across RAG agents and cannot be centralized. The proposed framework reduces unnecessary data
exposure by sharing embedding-space summaries for routing. However, this design does not address
two potential risks. In an agent-in-the-wild setting, malicious agents may return incomplete, misleading, or low-quality responses, and routing or evaluation errors may propagate across iterations,
especially for complex multi-hop questions. To reduce this risk, RIRS requires evidence-backed
responses, filters returned outputs through a server-side evaluator, and allows the system to stop or
declare a query unanswerable when adequate support is unavailable. A second concern is privacy
leakage: Similar to federated learning, the proposed RIRS offers a fundamental privacy protection
because centroid summaries are more restrictive than sharing raw documents. However, it still reveals
partial information about local knowledge, especially under repeated probing or after updates to an
agent’s corpus. An important direction for future work is to study how additional privacy-preserving
mechanisms, such as Gaussian or Laplace perturbation, affect routing accuracy, and to develop
stronger privacy-preserving summarization and access-control mechanisms that preserve comparable
performance.

Reproducibility Statement
We make reproducibility a priority in both the algorithmic design and the experimental setup. The
paper specifies the full RIRS pipeline, including the offline knowledge summarization stage, the
online query solving, the clustering objective, and the corresponding approximation algorithm. The
appendix further provides pseudocode, theoretical analysis, step-by-step procedures, and the prompt
templates used by the server modules and the RAG agents. The experimental section reports the
datasets, corpus construction, backbone models, baselines, evaluation metrics, and implementation
details needed to replicate the reported results. All methods are evaluated in an off-the-shelf setting
without task-specific fine-tuning. At the same time, exact reproduction remains challenging because
LLM-based generation is inherently stochastic, and this variance is amplified in multi-hop settings
where later rounds depend on earlier query rewriting and response evaluation. To reduce the impact
of randomness, each experiment is run three times, and the paper reports average results. We also
disclose the main system components used in our implementation, including retrieval, chunking,
model serving, and agent orchestration, and have released our code repository at GitHub to facilitate
close reproduction of the experiments.

A.2

Effectiveness of Knowledge Summarization

This subsection provides additional justification for centroid-based routing in RIRS. In the offline
stage (Section 4.1), each RAG agent partitions its local knowledge-piece embeddings into disjoint
clusters and uploads only the corresponding centroids to the server. At inference time, the server
routes a user query by retrieving the most similar centroids and selecting the associated agents/clusters.
The key intuition is that if a cluster is semantically coherent, then its centroid remains a reliable proxy
for locating that cluster (and thus the responsible RAG agent) using cosine similarity.

that centroid-based search is bounded: a query cannot be simultaneously very close to a relevant
knowledge piece and arbitrarily far from the centroid of the piece’s cluster. This bound clarifies when
centroid routing is reliable and how clustering quality (coherence) impacts routing robustness.

Practical design choices: TopK selection and square-root clusters. While the threshold-based
setup enables analysis, production deployment requires controllable routing cost and stable latency.
In RIRS, we therefore adopt two practical choices.
First, we select candidate clusters (and thus RAG agents) by TopK, as described in Section 4.2. A
similarity-threshold rule (select all centroids with similarity greater than a designated threshold) is
difficult to control: broad queries can match many centroids, leading to unpredictable fan-out and
unstable latency/cost. Although Theorem A.2 relates cluster coherence to query-centroid similarity,
any analytically "safe" threshold can be overly permissive in realistic regimes, still admitting many
weakly related clusters. In contrast, TopK is a direct, monotone cost knob and is commonly used to
achieve controllable latency and budget constraints.
√
Second, as mentioned in Section 4.1, we set the number of clusters per agent to n = ⌊ m⌋. This
heuristic is inspired by the success of inverted file indexing in database practice: it provides a
predictable, sublinear growth of the number of centroids, limiting server-side storage and similaritysearch cost. Intuitively, agents with more knowledge pieces may have more overlapping or redundant
content and thus can be represented with more clusters, while agents with fewer knowledge pieces
are often more specialized and do not require fine-grained partitioning. This design choice is also

may occupy the TopK list, decreasing the number of unique selected agents and harming performance
on cross-domain queries. For these reasons, we adopt the square-root heuristic and TopK selection as
a production-friendly default.
A.3

Server Modules

RIRS coordinates multiple RAG agents using a central server. Beyond routing, the server relies on
several server modules to (i) filter unreliable or irrelevant responses, (ii) consolidate evidence-backed
content, and (iii) refine queries when multi-hop reasoning is required. These server modules do
not maintain private knowledge bases; they operate only on the user query, the routed RAG agent
responses, and the quoted evidence returned by those RAG agents. Prompt templates are provided in
Figures 9 to 11.
Response Evaluator (Prompt in Figure 9). The Response Evaluator is the first checkpoint after
collecting responses from selected RAG agents. Since the server lacks domain-specific knowledge,
the evaluator uses a common-sense and logic-based assessment with three criteria: (i) Relevance:
whether the response helps answer the query (even if incomplete); (ii) Evidence-based support:
whether key claims are supported by explicitly quoted evidence; and (iii) Logical coherence: whether
the response is consistent and free of contradictions. For single-hop settings, the evaluator labels each
response as addressed or not addressed. For multi-hop settings, it further distinguishes fully addressed
from partially addressed among the addressed responses. This filtering is critical because irrelevant
RAG agents may still produce plausible but misleading responses; propagating such responses can
degrade summarization and cause error accumulation across rounds.
Response Summarizer (Prompt in Figure 10). The Response Summarizer consolidates evaluatorapproved responses into either a final answer or an intermediate solution. When at least one response
is labeled fully addressed, the summarizer produces the final answer by integrating evidence-backed
content from one or more fully addressed responses. When no response is fully addressed but some
are partially addressed, the summarizer first synthesizes a unified intermediate solution from the
valid partial evidence and then re-evaluates whether the unified solution fully resolves the query.
If it is deemed fully addressed, the summarizer outputs the final answer; otherwise, it outputs the
intermediate solution for query refinement. This design benefits from evaluator filtering, since
summarization is more reliable when the input is shorter and contains fewer irrelevant responses.
Question Simplifier (Prompt in Figure 11). When the current query is not fully resolved, the
Question Simplifier refines it for the next round. Given the original query and the current intermediate
solution, it: (i) identifies which components of the query have already been addressed (with evidence),
(ii) enumerates unresolved aspects that remain necessary for correctness, and (iii) generates a refined
query that removes resolved parts and focuses on unresolved aspects. This on-the-fly refinement
converts partial progress into a targeted next query, enabling iterative multi-hop progress without
requiring a rigid precomputed question decomposition plan.
A.4

Step-by-Step Procedure for Iterative Refining-Solving

The main body (Section 4.2) introduces iterative refining-solving at a high level. This subsection
presents a step-by-step procedure that clarifies how routing and server modules interact across rounds
for multi-hop queries.
Inputs. A user query q0 ; a server-side centroid index (uploaded by all RAG agents); a TopK value
K; and a maximum round limit T.
Outputs. A final answer with supporting evidence, or an explicit unanswerable outcome within the
current system scope.
21

Preprint. Under review.

Procedure. We maintain the current query qt and an intermediate solution state (e.g., evidencebacked partial progress) across rounds.
1. Initialize. Set t = 0 and qt = q0 . Initialize an empty progress record to store intermediate
solutions and the evidence used so far.
2. Route and collect responses (core of RTA NS).
(a) Embed the current query to obtain x = ϕ(qt ).
(b) Retrieve TopK centroids by similarity and map them to a deduplicated set of RAG agents
(i.e., if multiple selected centroids belong to the same agent, that agent is invited only once).
(c) Forward qt to the selected RAG agents in parallel.
(d) Each selected RAG agent runs its local RAG pipeline (retrieval → reranking → generation)
and returns an evidence-backed response.
3. Evaluate responses. Apply the Response Evaluator to label each response as fully addressed,
partially addressed, or not addressed. Discard responses labeled not addressed.
4. Terminate or refine.
(a) If any response is fully addressed: invoke the fully addressed summarizer to produce the final
answer and terminate.
(b) Else if there exist partially addressed responses: invoke the partially addressed summarizer to
synthesize an intermediate solution. If the summarizer deems the unified solution answerable,
output the final answer and terminate. Otherwise, proceed to Step 5.
(c) Else (all responses not addressed): terminate with an unanswerable outcome (see Section A.5).
5. Refine the query. Invoke the Question Simplifier using (qt , intermediate solution) to produce
a refined query qt+1 that focuses on unresolved aspects. Set t ← t + 1 and repeat from Step 2
unless t ≥ T.
Operational notes. TopK is the primary cost knob for controlling fan-out and latency. The round
limit T prevents runaway loops on ambiguous or out-of-scope queries. Deduplicating selected RAG
agents is important when an agent uploads many clusters; otherwise, multiple centroids from a single
agent may occupy the TopK list and reduce cross-agent coverage.
A.5

Discussion: Unhandleable Queries

Even with centroid-based routing and iterative refining-solving, some queries remain unanswerable
within the system scope or operational constraints. This can occur for several reasons: (i) the query
falls outside the knowledge coverage of all RAG agents; (ii) the query is ambiguous, underspecified,
or noisy (e.g., due to typos), hindering routing and retrieval; (iii) the relevant domain evolves rapidly,
and agents’ local knowledge bases become stale; or (iv) retrieval/evaluation fails under practical
constraints (timeouts, round limits), preventing evidence-backed progress.
Practical handling. In practice, systems typically adopt one of two policies. First, they may
return an explicit unanswerable response to the user and request rephrasing or additional context.
Second, they may escalate the query to a human expert, especially in high-stakes settings, optionally
forwarding the system’s intermediate progress and collected evidence to reduce human effort.
What we adopt in this work. Our handling differs across settings. In WikiAgents, a true humanexpert escalation is operationally expensive. We therefore approximate this pathway by invoking a
knowledgeable agent when RIRS fails to obtain any addressed responses (or reaches the round limit).
For multi-hop queries, the knowledgeable agent is given a simplified query produced by the Question
Simplifier when available, since reducing the number of reasoning steps is often beneficial (Zhuang
et al., 2024). In NewsAgent, each input query includes a label indicating whether it is solvable. For
queries labeled unsolvable (or when no evidence-backed, addressed responses are obtained), we
return an explicit unanswerable response to the user rather than attempting a fallback that could
increase hallucination risk in time-sensitive domains.

B.2

Agent Construction and Corpora

WikiAgents. WikiAgents is built over 121K Wikipedia pages (snapshot date: Nov. 1, 2023) and
contains exactly 64 agents. This number follows the limitation of the ORES legacy service, which
assigns Wikipedia pages into 64 predefined categories (Johnson et al., 2021); we map each category
to one agent so that agent specialization aligns with the ORES taxonomy. Because this taxonomy may
not cover all documents required by downstream questions, when retrieved evidence is insufficient,
the LLM may still respond based on its parametric knowledge. We account for this behavior in
evaluation by reporting both lexical match and LLM-judged accuracy (Section 5.1).
NewsAgents. NewsAgents is constructed from 609 news articles from 49 media outlets across six
domains (Tang & Yang, 2024). We consider two partitions: NewsAgent-Source (agents grouped by
outlet) and NewsAgent-Domain (agents grouped by domain). Each agent uses LLaMAIndex to split
articles into 256-token chunks with 20-token overlap between consecutive chunks.
B.3

Baselines

We reproduce baselines within our multi-agent evaluation framework. All methods are evaluated in
an off-the-shelf setting: we do not train any models, and instead rely on LLM capabilities.
Single-agent Scenarios. In the single-agent setting, the knowledge contained within all RAG
agents is merged into a single RAG system. This provides a conventional RAG baseline that can
retrieve from the entire corpus. Although it does not fully match the multi-agent routing scenario, it
illustrates challenges of large-scale retrieval (e.g., longer retrieval latency and increased distractors).
If retrieval were perfectly clean, the single-agent setup could be viewed as an approximate upper
bound for multi-agent accuracy when judged against ground truth; in practice, however, pooling all
documents increases the chance of retrieving distractors, especially for multi-hop queries.
• EfficientRAG (Zhuang et al., 2024): This approach iteratively simplifies/decomposes the query,
retrieving evidence at each step until the question becomes answerable. The simplification process is
performed by the LLM by removing resolved parts of the query; if further progress is not possible, a
knowledgeable agent produces the final answer. Our implementation follows EfficientRAG (Zhuang
et al., 2024) and is conceptually related to Self-ASK (Press et al., 2022), SelfRAG (Asai et al.,
2023b), and IM-RAG (Yang et al., 2024b).
Multi-agent Scenarios. In the multi-agent setting, we keep the same agent backends and retrieval
modules as RIRS, and only replace the routing mechanism.
• Chameleon (Lu et al., 2024a): A description-based router that prompts an LLM with agent
descriptions and selects the agents most relevant to the current query. For WikiAgents, each
description is derived from the corresponding ORES topic category. For NewsAgents, descriptions
are derived from either the news outlet or the domain, depending on the partition.
• RouterDC (Chen et al., 2024a): A learning-based router that represents each candidate agent with
a learned routing vector and selects agents by embedding similarity at inference time. To instantiate
this baseline in our setting, we collect 100 single-hop answerable questions for each WikiAgent
and use them to fit agent representations while keeping the embedding backbone fixed. We do
not report RouterDC on MHR because that benchmark does not provide enough agent-specific
supervision to train these representations reliably.

Performance when Excluding Knowledgeable Agents. Table 8 compares Chameleon, RouterDC,
and RIRS on 2WikiMultiHopQA and HotpotQA. Across both datasets, RIRS achieves the highest
answerable rate according to RAG and the highest RAG accuracy, indicating more reliable agent
selection and stronger evidence-grounded generation. Chameleon generally achieves higher RAG
accuracy than RouterDC, while RIRS improves on both dimensions, which helps explain its overall
accuracy gains. The CoT accuracy of these retrieval-based methods can be either higher or lower
than the CoT-only baseline, with no deterministic trend: if many RAG-unanswered questions are
still solvable via the model’s parametric knowledge, CoT accuracy can increase; conversely, if the
remaining unanswered questions are intrinsically difficult or poorly handled without evidence, CoT
accuracy can decrease.
Number of Required Agents. Figure 4 illustrates the distribution of questions by the minimum
number of required agents across three multi-hop QA datasets: MuSiQue, 2WikiMultiHopQA, and
HotpotQA. Although all three datasets consist of multi-hop questions, the necessary knowledge
pieces may sometimes reside within a single agent. In MuSiQue and 2WikiMultiHopQA, most
questions can be answered using two RAG agents, and all questions require no more than four agents.
For HotpotQA, all questions can be answered with just two agents. It is important to note that the
number of required agents does not directly correspond to the number of query rounds. Multiple
agents can be invoked simultaneously within a single round, and conversely, a single agent may be
queried multiple times to perform complex reasoning before reaching the final answer.
Query Rounds and Accuracy. Figure 5 presents the proportion of questions that can be answered
within different numbers of query rounds, along with the corresponding answer correctness. Across
all LLMs, most questions are resolved within the first two query rounds. Specifically, stronger models
(e.g., Qwen-Plus) can answer more questions compared to weaker ones (e.g., LLaMA-3.1-8B) within
fewer query rounds. Interestingly, the figure also shows that increasing the number of query rounds
does not necessarily lead to improved answer accuracy. In fact, unless a question inherently requires
multi-step reasoning, additional query rounds may result in even poorer performance.
This trend is consistent with the routing-error analysis in Section 5.3: additional rounds create more
opportunities for misrouting and for accumulating partially relevant evidence, which can distract the
generator. Therefore, accurate answerability judgment and effective stopping criteria are crucial for
controlling both latency and error accumulation.
